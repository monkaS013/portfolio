# Internal HRIS

*Português abaixo.*

A full-stack HR platform that replaced scattered spreadsheets and email approvals, plus a prototype that didn't scale. Around 20 functional modules, used daily across a company.

**Role:** sole engineer (requirements, architecture, full implementation, test suite, deploy, and a security review).
**Stack:** Next.js 16 (App Router, React 19) · TypeScript · Prisma 6 + PostgreSQL · Better Auth (email + Microsoft Entra SSO) · Microsoft Graph (app-only) · Docker.

## The problem

HR ran in pieces. The employee base lived in a BPM tool, contracts and amendments were handled by hand, approvals were loose email threads, reimbursements and benefits sat in spreadsheets. There was no single system covering people records, hiring, absences, contracts, benefits, and audit, with access control by role and LGPD compliance. An earlier Python prototype didn't scale, so this is a full rewrite in TypeScript.

## The architecture

- **Next.js App Router.** Server Components and Server Actions. Master data goes straight through Prisma; approval flows (hiring, absences) run on a generic process engine (engine + registry + rules + payloads) with task-based decisions in an inbox.
- **Authorization in depth, three layers.** A cheap session-cookie check plus CSP injection at the proxy, then session validation against the database in the authenticated layout, then a per-page/action re-check of session and RBAC through a `can()` function.
- **Pure rules ↔ IO.** Business rules live in pure, testable functions with no IO, kept apart from the files that do IO. Vacation rules, RBAC and CSP generation all sit on the pure side, and that split is what makes the large test suite possible.
- **Side effects after commit, and fault-tolerant.** Audit logging and email (via Microsoft Graph) run after the commit and never bring down the main operation. Integrations degrade gracefully with no credentials, so a feature missing them just goes dormant.
- **JIT provisioning.** Microsoft Entra SSO creates and reconciles the user on first login; an idempotent CLI/cron syncs the directory into Postgres.

## Engineering highlights

- **Granular, testable RBAC.** 7 roles × ~28 actions as a declarative matrix, plus visibility scoped by the management tree (a manager sees direct and indirect reports via BFS) and a multi-entity filter that isolates each group company. All in pure functions, covered by tests.
- **Hybrid approval.** Global actions through `can()`, plus task-based decisions in the inbox where the approver is the task's assignee. That gives dedicated approvers without inflating the role model.
- **Security hardening.** A per-request nonce CSP with `strict-dynamic` and no `unsafe-inline` scripts (anti-XSS), `frame-ancestors 'self'` (anti-clickjacking), generated by a pure, testable function. It followed a read-only security review across four axes, which didn't turn up SQLi, XSS, IDOR, path traversal, or SSRF.
- **Webhook and link safety.** The e-signature webhook is authenticated by a secret token in the path; email approval links (no login) are protected by an HMAC signature and expiry, since an email client carries no cookie.
- **Wide test suite.** 571 test cases across 53 files, focused on the pure rules for RBAC, vacation, reimbursement, contract amendments, invoice parsing, org tree and notifications.
- **Idempotent, crash-safe boot.** On start the container waits for Postgres, applies migrations, and runs an idempotent seed. If a migration fails the boot aborts, so the app never comes up on an inconsistent database.

## Results

- 571 automated tests across 53 files.
- RBAC with 7 roles and ~28 actions, scoped by management tree and isolated per group company.
- ~20 functional modules over ~30 data models.
- A clean internal security review across the OWASP axes above (an internal review, not an external certification).
- Continuous deploy on push, with quality gates (typecheck, lint, the full test suite, a smoke test) run locally before each push. There's no CI server, so the gate depends on discipline.

> Sanitized: no company identity, people, subsidiaries, internal URLs, financials, or seed credentials. Only a fictional seed is ever used.

# HRIS interno

Um portal de RH full-stack que substituiu planilhas soltas e aprovações por e-mail, mais um protótipo que não escalava. Cerca de 20 módulos funcionais, usados todo dia por uma empresa.

**Papel:** engenheiro único (requisitos, arquitetura, implementação completa, suíte de testes, deploy e uma revisão de segurança).
**Stack:** Next.js 16 (App Router, React 19) · TypeScript · Prisma 6 + PostgreSQL · Better Auth (e-mail + SSO Microsoft Entra) · Microsoft Graph (app-only) · Docker.

## O problema

O RH rodava em pedaços. A base de colaboradores vivia numa ferramenta de BPM, contratos e aditivos saíam no braço, as aprovações eram threads de e-mail soltas, reembolsos e benefícios ficavam em planilhas. Não havia um sistema único cobrindo cadastro, contratação, ausências, contratos, benefícios e auditoria, com controle de acesso por papel e conformidade LGPD. Um protótipo Python anterior não escalava, então este é uma reescrita completa em TypeScript.

## A arquitetura

- **Next.js App Router.** Server Components e Server Actions. Dado mestre vai direto pelo Prisma; os fluxos com aprovação (contratação, ausências) rodam num motor de processos genérico (engine + registry + rules + payloads) com decisão task-based num inbox.
- **Autorização em profundidade, três camadas.** Checagem barata do cookie de sessão mais injeção de CSP no proxy, depois validação da sessão no banco no layout autenticado, depois uma revalidação por página/ação de sessão e RBAC via função `can()`.
- **Regra pura ↔ IO.** As regras de negócio ficam em funções puras, testáveis, sem IO, apartadas dos arquivos que fazem IO. Regras de férias, RBAC e geração de CSP estão todas do lado puro, e é essa separação que sustenta a suíte de testes grande.
- **Efeitos colaterais pós-commit e tolerantes a falha.** Auditoria e e-mail (via Microsoft Graph) rodam depois do commit e nunca derrubam a operação principal. As integrações degradam graciosamente sem credenciais, então o recurso que não as tem simplesmente fica dormente.
- **Provisionamento JIT.** O SSO Microsoft Entra cria e reconcilia o usuário no primeiro login; um CLI/cron idempotente sincroniza o diretório no Postgres.

## Destaques de engenharia

- **RBAC granular e testável.** 7 papéis × ~28 ações como matriz declarativa, mais visibilidade escopada pela árvore de gestão (o gestor vê subordinados diretos e indiretos por BFS) e um filtro multi-empresa que isola cada empresa do grupo. Tudo em funções puras, coberto por testes.
- **Aprovação híbrida.** Ações globais via `can()`, mais decisões task-based no inbox onde o aprovador é o assignee da task. Isso dá aprovadores dedicados sem inflar o modelo de papéis.
- **Hardening de segurança.** CSP com nonce único por request, `strict-dynamic` e sem script `unsafe-inline` (anti-XSS), `frame-ancestors 'self'` (anti-clickjacking), gerada por uma função pura e testável. Veio depois de uma revisão de segurança read-only em quatro eixos, que não achou SQLi, XSS, IDOR, path traversal nem SSRF no código.
- **Segurança de webhook e link.** O webhook de assinatura é autenticado por um token secreto no path; os links de aprovação por e-mail (sem login) são protegidos por assinatura HMAC e expiração, já que o cliente de e-mail não carrega cookie.
- **Suíte de testes ampla.** 571 casos de teste em 53 arquivos, focados nas regras puras de RBAC, férias, reembolso, aditivos, parsing de fatura, árvore organizacional e notificações.
- **Boot idempotente e à prova de falha.** No start o container espera o Postgres, aplica as migrations e roda um seed idempotente. Se uma migration falha, o boot aborta, então o app nunca sobe sobre um banco inconsistente.

## Resultados

- 571 testes automatizados em 53 arquivos.
- RBAC com 7 papéis e ~28 ações, escopado pela árvore de gestão e isolado por empresa do grupo.
- ~20 módulos funcionais sobre ~30 modelos de dados.
- Uma revisão de segurança interna limpa nos eixos OWASP acima (revisão interna, não uma certificação externa).
- Deploy contínuo por push, com gates de qualidade (typecheck, lint, a suíte inteira, um smoke test) rodados localmente antes de cada push. Não há servidor de CI, então o gate depende de disciplina.

> Sanitizado: sem identificação da empresa, pessoas, subsidiárias, URLs internas, valores financeiros ou credenciais de seed. Só um seed fictício é usado.
